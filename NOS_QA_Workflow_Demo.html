The 7-Stage Workflow

From Jira story to ISO test plan document

End-to-End Workflow Pipeline

#StageWhat HappensAI?Output
1 Jira Story Select EXOS release → auto-fetch Jira story details (title, description, type, priority) — Workflow created in DB
2 Skill File AI generates structured feature knowledge file from Jira description. Reviewer approves. GPT-4o Approved skill .md file
3 Test Plan AI generates comprehensive test plan with test cases from skill file. Editable Markdown preview. GPT-4o Test plan document
4 TC Classification AI classifies each TC as Manual / Semi-Automatable / Automatable. Bulk or individual override. GPT-4o-mini Classified TCs in DB
5 Script Generation Generates TCL regression scripts for automatable test cases. GPT-4o TCL script files
6 TC Execution Track pass/fail/blocked for each TC. Notes, build version, platform. Pie chart summary. — Execution results
7 Workflow Completion Final summary report. ISO DOCX export. qTest upload. Mark workflow complete. — ISO DOCX + qTest

Stage 1 & 2 — Story Selection + Skill File

📋 Stage 1: Jira Story Selection

  • Select EXOS release (e.g. EXOS 34.1)
  • Dropdown auto-populated from Jira REST API
  • Stories filtered by project key + fix-version
  • Auto-captures: title, description, type, priority, status, labels
  • Supports manual story ID override
  • Detects New Feature vs Enhancement automatically
  • Creates workflow record + audit entry in DB

🤖 Stage 2: AI Skill File Overview

  • AI orchestrates 5 data sources simultaneously
  • Generates 8-section functional specification document
  • Cites actual function names from git commits
  • Includes real CLI commands from EXOS command reference
  • Full Markdown editor — manual edits tracked in amendment log

🔒 Quality Gate: Stage 3 is locked until an approver reviews the Skill File. This ensures every test plan is grounded in validated, human-reviewed feature knowledge.

Stage 2 — Skill File Generation (Deep Dive)

🔀 5 AI Input Sources

  • 1
    Jira Story

    Title, description, acceptance criteria, labels, type — the primary context

  • 2
    Git Commit Analysis

    Analyzes EXOS repo commits tagged with the story ID — extracts real function names, modified files, data structures (e.g. lldpFaProcessBypassNl() in lldpFa.c)

  • 3
    Default Skill Templates

    Up to 10 most similar approved skill files from knowledge base — scored by keyword matching against story

  • 4
    EXOS Command Reference

    Top 5 most relevant sections from EXOS 33.7.1 command reference (8 KB extracted per generation)

  • 5
    Uploaded Reference Docs

    Optional: PRD, MRD, previous test plan DOCX — parsed and injected as context

📄 8-Section Skill File Structure

#SectionKey Content
1Feature OverviewPurpose, use cases, standards, prerequisites
2Functional DescriptionHow it works step-by-step, state transitions, default behaviour
3EXOS ImplementationReal function names, modules, data structures from commit analysis
4Attributes & ParametersAll config options, valid ranges, defaults, platform variations
5CLI CommandsAll config & show commands with syntax, examples, actual output
6Feature InteractionsIntegration with VLAN, routing, ACL, QoS, security
7Operational CharacteristicsScale limits, CPU/memory, HA behaviour, failover, logging
8Known Issues & LimitationsPlatform limitations, restrictions, future work

🤖 Model: claude-opus-4-8 (heavy) · Commit integration is mandatory — generic output is rejected

📐 7 Universal Test Categories

  • Cat 1 Basic Functionality — enable/disable, all config commands, show commands
  • Cat 2 Boundary Value — all parameter limits, min/max/edge values
  • Cat 3 State Machine — all states and valid/invalid transitions
  • Cat 4 Switch Events — reboot, MSM failover, port flaps, persistence
  • Cat 5 Integration — VLAN, routing, ACL, QoS, other EXOS subsystems
  • Cat 6 Scaling & Performance — max capacity, throughput, CPU under load
  • Cat 7 Negative Testing — invalid inputs, error handling, rejection cases

How AI is Used Throughout

🧠 Skill File Generation

claude-opus-4-8 fuses 5 sources: Jira story, git commit analysis (real function names), top-10 matched skill templates, EXOS command reference, and uploaded docs → 8-section feature spec. Stage 2

📋 Test Plan Generation

claude-opus-4-8 uses approved skill file + guidelines. Detects New Feature vs Enhancement automatically — different category coverage + TC count targets. Streams in real time. Stage 3

🏷️ TC Classification

claude-sonnet-4-6 evaluates each TC's methodology steps — determines Manual / Semi-Automatable / Automatable with rationale. Bulk or per-TC mode, override supported. Stage 4

⚡ Script Generation

claude-opus-4-8 generates TCL/NOS API regression scripts for automatable TCs using nosApiTester framework conventions and EXOS scripting patterns. Stage 5

💬 AI Chat Advisor

Context-aware chat on every stage. AI knows the current workflow's skill file, test plan, and TCs. Can re-classify, improve TCs, explain decisions, answer protocol questions. All Stages

📊 Guidelines-Driven Quality

All prompts anchored to TEST_PLAN_GENERATION_GUIDELINES.md — 1,000+ lines defining TC format, 15-section mapping, good/bad examples, and EXOS CLI requirements. Quality Control

Stage 6 — TC Execution Tracking

📊 Execution Dashboard Features

  • Per-TC result recording: Pass / Fail / Blocked / Not Run
  • Notes & updated methodology per execution
  • Platform + build version tags
  • Execution session management (group by date/build)
  • Real-time pie chart: colour-coded by result
  • Pass rate calculation with trend
  • Bulk result update support
  • Export execution results to XLSX

🎨 Result Color Coding

Pass — TC verified successfully
Fail — TC did not meet criteria
Blocked — dependency / environment issue
Not Run — pending execution
Skipped — deferred or N/A

All execution results are stored with timestamp, user, session ID, and build version for full traceability.

ISO DOCX Documentation

Extreme Networks standard test plan format — auto-generated

Stage 7 — ISO Format DOCX Export

📄 DOCX Document Structure

  • 📌 Title: "EXOS Functional Test Plan"
  • Release Information table (story, author, version, date)
  • Revision History table
  • 📋 Section 1: Introduction (Overview, Use Cases, Terminology)
  • 🌐 Section 2: Topology (placeholder)
  • ⚙️ Section 3: Set up and Configurations
  • 🔧 Section 4: Tools (IXIA, RADIUS)
  • 📝 Section 5: Test Cases — 15 sub-sections (5.1–5.15)
  • Each TC: methodology, pass criteria, sanity flag
  • 📎 Section 6: Appendix A (References)
  • 📅 Section 7: Appendix B (Meeting Minutes)
  • ✅ Section 8: Review Meeting Action Items

🎯 Smart TC Routing to Sections

Test cases are automatically routed to the correct section based on title/description keywords:

# Keyword-based routing examples
"reboot" / "restart" → 5.6 Redundancy
"cli" / "configure" → 5.4 CLI Config
"snmp" / "mib" → 5.5 SNMP MIB
"negative" / "invalid"→ 5.14 Negative
"stress" / "memory" → 5.15 Stress
# Default (no match): → 5.2 Feature Spec

Empty sections are never omitted — they show a "—" placeholder so the document always conforms to the complete 15-section Extreme Networks FTP template.

Robustness & Quality

Built to be reliable, auditable, and maintainable

System Robustness

🛡️ Security

  • JWT Bearer token authentication on all API routes
  • bcryptjs password hashing (no plain-text storage)
  • Role-based access: admin routes reject non-admins
  • Stage 3+ locked until Skill File approved
  • Input validation at all API boundaries
  • OWASP-aware: no SQL injection (parameterised queries)

🔄 Error Handling

  • Graceful LLM fallback (GitHub Models → Ollama)
  • BOM-safe Python stdin parsing for DOCX generation
  • Streaming abort on client disconnect
  • Stage gate validation before progression

🧪 System Tests (23 Checks)

Automated health check suite in Admin → System Tests:

  • API server reachable (GET /health)
  • Valid login accepted / invalid rejected
  • Session token validation
  • All workflow API fields present
  • Stage 9 summary report structure
  • Database connection & all required tables
  • Admin user exists in DB
  • DB file on disk (with size check)
  • Uploads directory writable
  • Python DOCX script present
  • Node.js version ≥ 14
  • Server memory not critically low
